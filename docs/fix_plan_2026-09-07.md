## 0. 修复原则

1. **兼容优先**：所有改动不得破坏现有生产流水线（90s 循环 + gunicorn + sync_loop 的部署形态不变），除非该项明确标注"需要部署配合"。
2. **验证先行**：每项改动附带验证命令；W1 完成后要求 `pytest` 全绿、`py_compile` 全绿。
3. **可回滚**：数据库类改动（S2 数据归一、L3 索引清理、L4 唯一约束）必须提供 dry-run 与回滚脚本；代码类改动保留旧函数别名（如 MD5 版 hash）供对比。
4. **文档同步**：每波完成后按 `docs/project_context_index.md` §10 要求回填受影响的专项文档。
5. **建议前置：`git init`**（当前目录不是 git 仓库）。任何批量修复前先建立版本基线，否则无法回滚。若用户不同意建仓，则改为逐项备份被改文件到 `docs/fix_backups/`。

### 1.2 [S2] 统一 content_hash 为 blake2b（核心数据修复）

**代码统一**：

- `utils.py`：将 `compute_content_hash` 的实现替换为 `news_fetcher.py` 现有的 blake2b 实现（保持签名不变）：

```python
def compute_content_hash(title: str, content: str) -> str:
    """基于标题+正文计算内容哈希（blake2b，64 hex），用于跨来源去重。统一实现。"""
    raw = f"{title}\n{content}".encode("utf-8", errors="replace")
    return hashlib.blake2b(raw, digest_size=32).hexdigest()
```

- `news_fetcher.py`：删除本地重复定义，改为 `from utils import compute_content_hash`（utils 不依赖 news_fetcher，无循环导入；`_dedupe_by_hash` 自动跟随）。
- 保留 MD5 旧实现为 `utils.compute_content_hash_legacy_md5()`（仅作回滚/对比用，注释标明"勿在生产使用"）。
- `scripts/backfill_12h_windows.py`：无需改动（从 utils 导入，自动获得 blake2b）。
- `tests/test_news_fetcher.py::test_compute_content_hash`：断言 `len(h1) == 64`（并补充一条 blake2b 特性断言，如同内容不同 key 分隔符不可混淆——与原测试等价）。

**数据归一脚本（新增 `scripts/normalize_content_hash.py`）**：

```text
用法：
  python scripts/normalize_content_hash.py --dry-run   # 只报告受影响行数
  python scripts/normalize_content_hash.py --update    # 重算三表全部 content_hash（blake2b）
  python scripts/normalize_content_hash.py --dedupe    # （可选，在 --update 后）合并重复行保留最小 id，级联 selected/detail 重新指向
```

- 行为：遍历 `raw_news`，按 `title/content` 重算 blake2b；仅更新与现值不同的行；逐表输出统计。
- `--dedupe` 只在 `--update` 后使用：找出 `raw_news` 中重复 hash 组，保留 `MIN(id)`，将 `selected_news`/`news_analysis_detail` 中指向被删 id 的行改指保留 id 后删除冗余 raw 行。
- **验证**：W0-3 的 distinct 计数对比；抽查 3 条新闻三表 hash 一致；`pytest` 绿。
- **风险/回滚**：高风险。实施前必须备份；dry-run 输出与预期一致才 `--update`；若线上从未跑过 backfill，受影响行数应为 0（可跳过 --update）。
